# Архитектура

## 1. Главный принцип

```
  ┌──────────────┐   команды (Input → Command)   ┌───────────────────────┐
  │  Ввод / UI   │ ─────────────────────────────▶│                       │
  └──────────────┘                               │   ЯДРО СИМУЛЯЦИИ      │
                                                 │   (core/, без Node,   │
  ┌──────────────┐   снимок состояния (read-only)│   без графики,        │
  │ Виды: 2D,    │ ◀─────────────────────────────│   детерминированное)  │
  │ 2.5D, 3D,    │                               │                       │
  │ звук, HUD    │   события (EventBus)          │                       │
  └──────────────┘ ◀─────────────────────────────└───────────────────────┘
                                                            ▲
                                                            │ загружает
                                                 ┌──────────┴────────────┐
                                                 │ Данные / моды (JSON + │
                                                 │ ресурсы), ContentDB   │
                                                 └───────────────────────┘
```

- **Ядро** (`game/core/`) — чистые классы `RefCounted`. Не наследуются от `Node`, не трогают сцену,
  не читают ввод напрямую, не знают про графику. Запускаются в headless-тестах.
- **Виды** (`game/views/`) читают снимок состояния и рисуют. Можно иметь 2D-карту и 3D-кабину одновременно.
- **Ввод** превращается в **команды** (`SetControllerPosition`, `SetBrakeValvePosition`, `ToggleSwitch`…).
  Это даёт: запись/воспроизведение поездок, обучение с подсказками, ИИ-машиниста, будущий мультиплеер.
- **Контент** приходит только через `ContentDB`, который собирает данные из базовой игры и модов.

## 3. Ядро симуляции

### 3.1 Время
- Фиксированный шаг **`SimConfig.SIM_DT = 1/60 с`** (`FixedStepClock` в ядре, автозагрузка `SimClock` кормит его временем кадра), независимо от FPS.
- Множитель времени (×1, ×2, ×4 — только вне режимов оценки), пауза.
- Подсистемы с разной частотой: динамика поезда — каждый шаг; пневматика — каждый шаг
  (может потребовать подшагов); ИИ-диспетчер — 1–2 Гц; ИИ-поезда — 10 Гц упрощённо.

### 3.2 Единицы измерения
**Внутри ядра — только СИ:** м, с, кг, Н, Па, В, А, рад. Конверсия в «железнодорожные» единицы
(км/ч, кгс/см², тс, ‰) — **только** в `core/units.gd` и в UI. Это правило в GEMINI.md, нарушать нельзя.

### 3.3 Модель пути
- `TrackGraph`: узлы (`TrackNode` — стрелки, концы путей, точки соединения) и рёбра (`TrackSegment`). Подробно — D-005 в DECISIONS.md.
- `TrackSegment`: `id`, `length_m`, массив профиля (точки изменения уклона, ‰), массив кривых (радиус),
  ограничения скорости, электрификация (`ac_25kv`, `dc_3kv`, `none`), номер пути, принадлежность станции/перегону.
- Геометрия для отрисовки хранится отдельно (`polyline` в локальных метрах, проекция UTM 36N / EPSG:32636),
  ядро её не использует — ему нужны только длины, уклоны, кривизна.
- `TrackPosition { segment_id, offset_m, direction }` + метод `advance(distance)` с проходом через стрелки.
- Пикетаж/километраж (км + пикет) — атрибут, нужен для предупреждений и переговоров («на 23 км пикет 4…»).

### 3.4 Модель поезда
- `Consist` = список `Vehicle` (головной вагон, моторный, прицепной — по схеме состава).
- MVP: поезд как **одна точечная масса** с распределёнными по длине силами уклона/кривой (учёт длины состава).
- Позже: многомассовая модель со сцепками (пружина-демпфер) — для локомотивной тяги и грузовых.
- Подробные уравнения — в [SIMULATION.md](SIMULATION.md).

### 3.5 Системы поезда
Каждая система — объект с `step(dt, inputs) -> outputs` и явными зависимостями:
`Electrical` (токоприёмник, ГВ, тяговый трансформатор/выпрямитель, ТЭД, вспомогательные цепи, АКБ),
`Pneumatic` (ГР, компрессоры, ТМ, ТЦ, кран машиниста, ЭПТ), `Doors`, `Lights`, `Safety`.
Состояния кабины (позиции тумблеров) — в `CabState`, привязка тумблеров к цепям — **в данных** состава.

### 3.6 События
`EventBus` — типизированные события ядра: `SignalPassed`, `StationStopped`, `RuleViolation`,
`RadioMessage`, `SystemFault`… Виды/звук/оценка подписываются, ядро ни от кого не зависит.

### 3.7 Сохранения и повторы
- Сохранение = сериализация `SimWorld` в JSON (+ версия формата).
- Повтор = начальное состояние + лог команд с метками тиков. Детерминизм обязателен (не использовать
  `randf()` без сидированного `RandomNumberGenerator` из `SimWorld`).

## 4. Форматы данных

Все форматы описываются JSON Schema в `schemas/` и проверяются в CI (`tools/validate_data.py`).
Каждый числовой параметр, взятый не из надёжного источника, помечается в соседнем поле `_source`
или блоком `meta.verified: false`.

### 4.1 Подвижной состав (`rolling_stock/<id>/vehicle.json`, сокращённо)
```json
{
  "id": "er9m_mvag",
  "series": "ЕР9М",
  "type": "motor_car",
  "meta": { "verified": false, "sources": [] },
  "mass_empty_kg": 0,
  "length_m": 0,
  "axles": 4,
  "powered_axles": 4,
  "rotational_inertia_coef": 0.0,
  "resistance": { "model": "davis", "a": 0.0, "b": 0.0, "c": 0.0, "units": "N_per_kN" },
  "traction": { "curve_ref": "traction_curves.json#er9m" },
  "brakes": { "brake_cylinders": 0, "max_bc_pressure_pa": 0 },
  "visual": { "sprite_2d": "...", "model_3d": "..." }
}
```
Значения `0` в примере — заглушки: реальные числа заполняются по RESEARCH.md.

### 4.2 Состав (`consist.json`)
Схема формирования: например ЕР9М — `Гв + Мв + Пв + Мв + …` (уточнить штатное формирование, см. RESEARCH.md).

### 4.3 Кабина (`cab.json`)
Список органов управления: `id`, тип (`switch2`, `switch3`, `button`, `rotary`, `lever`),
позиции, хоткеи, к какой цепи/системе привязан, координаты на 2D-пульте (и позже — в 3D).

### 4.4 Маршрут (`routes/<id>/route.json`)
`track_graph.json` (узлы/сегменты), `geometry.json` (полилинии для отрисовки),
`stations.json` (станции, платформы с координатами по пути, пути, стрелки),
`signals.json` (светофоры: тип, позиция, к какому блок-участку относится),
`speed_limits.json`, `timetable.json`.

### 4.5 Сценарий (`scenarios/<id>.json`)
Стартовая позиция, состав, время суток, погода, задачи (цели), особые условия
(предупреждения, неисправности), критерии оценки, связь с уроком обучения.

## 5. Мод-система

**Базовая игра = мод `base`.** Тот же загрузчик грузит и её, и пользовательские моды.

```
mods/my_mod/
├── mod.json        # id, name, version, api_version, depends[], load_after[], authors, license
├── rolling_stock/  # JSON + текстуры/модели/звуки
├── routes/
├── scenarios/
└── locale/
```

- `ModLoader` (autoload) сканирует `res://content/`, `res://../mods/` (dev) и `user://mods/`,
  строит граф зависимостей, грузит по порядку, регистрирует всё в `ContentDB`.
- Ресурсы (модели, текстуры, звуки) — либо «сырыми» файлами (загрузка в рантайме: `Image.load`,
  `AudioStreamOggVorbis.load_from_file`, `GLTFDocument`), либо упакованными `.pck`
  через `ProjectSettings.load_resource_pack()`.
- **Безопасность:** в MVP моды содержат **только данные и ресурсы, без скриптов**. Скриптовые моды —
  отдельное решение позже (песочница / белый список API).
- Переопределение: мод может заменить сущность по тому же `id` только при явном `"override": true`.
- Совместимость: `api_version` (semver); несовместимые моды отключаются с понятным сообщением.
- Позже: внутриигровой браузер модов (каталог в отдельном GitHub-репозитории или mod.io).

## 6. Отрисовка по этапам

| Этап | Карта | Кабина / вид вперёд |
|---|---|---|
| M2 | 2D-схема `Node2D` (линии пути, поезд, сигналы) | отладочный HUD |
| M3–M8 (2.5D) | 2D-схема | 2D-пульт (`Control`, кликабельные элементы, стрелочные приборы) + `SubViewport` с простым 3D-видом вперёд: процедурный путь из геометрии, столбы КС, светофоры, платформы |
| M9 (3D) | 2D-схема как карта | полная 3D-кабина `.glb`, модели составов, окружение, LOD, стриминг |

Вид вперёд строится из той же геометрии маршрута (`geometry.json` + профиль высот), поэтому
2.5D-этап — не выброшенная работа, а «серый блок-аут» будущего 3D.

## 7. Локализация
`TranslationServer`, `.po`-файлы. Основной язык — **українська**, затем русский и английский.
Все строки UI — через `tr()`. Термины ПТЕ не переводить «по смыслу» — держать глоссарий в `docs/GLOSSARY.md` (создать в M0).

## 8. CI (GitHub Actions, `.github/workflows/ci.yml`)
1. **data** — `tools/validate_data.py` (схемы + перекрёстные ссылки) и юнит-тесты валидатора.
2. **lint** — `gdformat --check game/`, `gdlint game/`.
3. **godot-tests** — Godot 4.7.2 headless: `--import` (регистрирует `class_name`), затем `-s res://tests/run_tests.gd`.
4. (Позже) Экспорт сборок Windows/Linux по тегу.

Локально то же самое: `make check`.

| `sim.js` | порт `core/` 1:1 (UMD: браузер и node) |

## 11. Настольная демка 0.3.1

`views/exterior/ExteriorView` расширяет `RailView`: ортографическая 3D-сцена в пустом
пространстве, перспективная камера из кабины и прежняя аффинная проекция 2.5D.
`TrainCar3D` разделяет кузов, бегущие колёса и створки дверей. `RenderPose` хранит
два состояния головы между фиксированными тиками; вся графика использует одну долю
интерполяции. Фильтр сопровождения решает движение камеры по линейно движущейся
цели аналитически, с одинаковой задержкой при разных FPS. Ядро не зависит от рендера.
Рельсы, шпалы, балласт и КС объединены в MultiMesh по 200-метровым участкам с отсечением
дальних участков. Поле/небо отсутствуют. Камеры и аудиогруппы настраиваются через F3.

`TrainAudio` играет заранее подготовленные WAV OpenSFX; ритм осей смешан офлайн и
не зависит от количества кадров. Нарастание/затухание сигналов задаёт SignalEnvelope,
после отпускания сохраняется хвост 0,45/0,35 с. Автоматические объявления приглушают
шум поезда. CabControls и Announcer имеют отдельные аудиошины. Щелчки привязаны к
успешно изменившим состояние командам. Источники/изменения/лицензии лежат рядом с WAV.

`StationCues` подавляет повторные объявления, `StationAnnouncer` воспроизводит 41
готовую украинскую фразу и субтитры; user://announcements/ перекрывает встроенные WAV.
Модель TTS в приложении не нужна. Это синтезированные фразы, не голос реального оператора.

`geometry.json.map_features` — необязательные слои карты (пока river, точки local_m).
Их читает только вид. `kyiv_city_ring` содержит 20 настоящих названий/порядок остановок;
иллюстративная геометрия, платформы, плоский профиль и скорости помечены verified:false.
Это не импорт OSM и не выполнение M5 со сверенными инфраструктурными данными.

Двери — два тумблера CabState; открытие требует остановки и кіл керування, сбрасывает
контроллер и блокирует тягу. Свисток — отдельный удерживаемый орган. Изменения ядра
зеркалятся в JS. Проверка существующей траектории из 801 образца не изменилась.

`tools/build_desktop.py` создаёт один EXE со встроенным PCK и universal Mac .app в DMG.
GitHub Actions собирает DMG штатным hdiutil на macOS, проверяет codesign/lipo, запускает
Mac-приложение и EXE на Windows до публикации в Releases. SHA256SUMS.txt сопровождает
файлы. Локальный Linux-кросс-экспорт проверяет структуру, не заменяя запуск на целевых ОС.

WAV собираются из зафиксированного OpenSFX и проверенной по SHA256 модели Ukrainian TTS
в отдельном Linux-задании `audio`, затем передаются на macOS через Actions artifacts.
Это не требует Git LFS-квоты для генерируемых файлов. В Git остаются инструменты,
импортные метаданные, лицензии и атрибуция; бинарные WAV внутри релизов самодостаточны.
